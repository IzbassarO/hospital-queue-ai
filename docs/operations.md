# Эксплуатация

Регламент для того, кто разворачивает и ведёт Aqyl Kezek (hospital-queue-ai) на сервере ведомства или оператора.
Первый запуск, продакшн-топология, ежедневный регламент, резервные копии, обновление, закрытый контур.

Соседние документы: [integration.md](integration.md) — как встроить систему в контур (три способа, входной контракт,
ночной пересчёт по шагам); [security.md](security.md) — модель угроз и что должен добавить контур;
[monitoring.md](monitoring.md) — какие метрики смотреть и их базовые значения; [architecture.md](architecture.md) —
границы кода. Здесь только команды и эксплуатационные решения.

## 1. Из чего состоит развёртывание

| Сервис | Образ | Что делает | Порт в контейнере |
|---|---|---|---|
| `postgres` | `postgres:16-bookworm` (по digest) | read-модели, решения специалистов, ключи, журнал доступа | 5432 |
| `backend` | `hqai-backend` (`backend/Dockerfile`) | FastAPI `/api/v1`, миграции Alembic при старте | 8000 |
| `frontend` | `hqai-frontend` (`frontend/Dockerfile`) | nginx: статика интерфейса и прокси `/api` | 80 |
| `seed`, профиль `demo` | `hqai-backend` | разовая загрузка `seed/` в пустую базу | — |
| `pipelines`, профиль `pipelines` | `hqai-ml` (`ml/Dockerfile`) | офлайн-конвейер ML вне рантайма API | — |

Состояние: один том `pgdata`. Остальное монтируется с хоста только на чтение (`./seed`, `./db/init.sql`,
`./ml/configs`). Сервисы профилей `demo` и `pipelines` не запускаются обычным `docker compose up`.

Сервер под весь стек: ориентир 8 vCPU / 32 ГБ — это расчёт, а не замер на таком сервере; всё, что ниже помечено
«замерено», замерено на ноутбуке (10 ядер, 16 ГБ). Диск: на машине разработки с полными национальными данными
`pg_database_size` даёт 3,2 ГБ; база, поднятая только из `seed/` (30 МБ в репозитории), меньше, но отдельно
не замерена.

## 2. Первый запуск

Что должно стоять на машине: Docker Engine 25 или новее и Docker Compose v2.24+ (`docker --version`,
`docker compose version`). Более старая Compose не понимает `!reset` в переопределении и профили в том виде, в
котором они здесь используются. Больше ничего: ни Python, ни Node, ни доступа к данным Минздрава.

Демо-вариант, он же проверка машины:

```bash
git clone <repo> && cd hospital-queue-ai
make demo       # .env со случайным паролем и ключом -> сборка и старт -> загрузка seed/ -> make smoke
```

Замерено на чистой копии: 3 мин 47 с от клона до работающего продукта, из них большая часть — сборка двух образов.
`make smoke` в конце проверяет живость API, три публикации и интерфейс и печатает идентификатор публикации.

Продакшн-вариант — тот же compose плюс наложение `docker-compose.prod.yml` (раздел 3):

```bash
cp .env.example .env && $EDITOR .env        # POSTGRES_PASSWORD, DEMO_API_KEY, UI_BIND, FORWARDED_ALLOW_IPS
make prod-config                            # проверка, что наложение собирается
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build --wait
docker compose -f docker-compose.yml -f docker-compose.prod.yml --profile demo run --rm seed   # только на пустой базе
```

`DEMO_API_KEY` в контуре — временная мера для показа; рабочие ключи выдаются по одному на человека
(`make create-key ROLE=… LABEL=…`), после чего демо-ключ из `.env` убирается, иначе доступ к порту интерфейса равен
доступу к данным ([security.md](security.md) §3).

## 3. Продакшн-топология (`docker-compose.prod.yml`)

Наложение не меняет образы и схему, меняет доступность и пределы:

| Что | Демо (`docker-compose.yml`) | Наложение `docker-compose.prod.yml` |
|---|---|---|
| Порт PostgreSQL | `127.0.0.1:5432` | не публикуется, только `expose` внутри сети |
| Порт API | `127.0.0.1:8000` | не публикуется, только `expose` внутри сети |
| Порт интерфейса | `${UI_BIND}:${FRONTEND_PORT}` | тот же — единственная точка входа, её и закрывают TLS-терминатором |
| uvicorn | один воркер, `--proxy-headers` | `--workers 2 --proxy-headers --forwarded-allow-ips=${FORWARDED_ALLOW_IPS}` |
| Журналы контейнеров | json-file без границ | json-file, `max-size 20m`, `max-file 5` (у `pipelines` — 50m) |
| Пределы ресурсов | нет | `deploy.resources.limits` на каждый сервис |
| `/docs`, `/redoc`, `/openapi.json` | открыты | закрыты (`DOCS_ENABLED=false`); контракт поставляется файлом `backend/openapi.json` |
| Перезапуск | `unless-stopped` | `unless-stopped`, разовые сервисы — `no` |

`FORWARDED_ALLOW_IPS` — сеть того, кто стоит перед интерфейсом и терминирует TLS. По умолчанию
`172.16.0.0/12` (диапазон сетей Docker, то есть контейнер nginx из этого же compose). uvicorn принимает
`X-Forwarded-For` только с этих адресов, поэтому в журнале доступа остаётся адрес настоящего клиента, а не прокси.
Если TLS терминирует внешний балансировщик, укажите его сеть.

Пределы по умолчанию: postgres 2 CPU / 4 ГБ, backend 2 CPU / 2 ГБ, frontend 1 CPU / 256 МБ, pipelines 6 CPU / 16 ГБ.
Пределы `pipelines` важны не только для безопасности: `ml/` подбирает размер буфера DuckDB и число потоков по
доступной памяти, а этот блок входит в идентичность плана запуска. Проверено: один и тот же `--plan` на хосте, в
`docker run` без пределов и через `docker compose run` (где действует `DUCKDB_MEMORY_LIMIT` из `.env`) даёт три
разных `scientific_identity_sha256` при одном коде и одних данных. Поэтому ночной цикл всегда запускают с одними
пределами и одним `DUCKDB_MEMORY_LIMIT`, а план перед расчётом сверяют командой `--plan`.

Что проверено: `docker compose -f docker-compose.yml -f docker-compose.prod.yml config` (цель `make prod-config`,
тот же шаг в CI на каждый push, поэтому наложение не разойдётся с основным файлом). Полный запуск этой топологии
на отдельном сервере ещё не отрепетирован — на машине разработки заняты те же порты и имена контейнеров.
Чего в наложении сознательно нет: `read_only` + tmpfs для nginx, отдельный разовый сервис миграций, TLS и SSO —
см. раздел 11.

## 4. PostgreSQL

Образ — обычный upstream `postgres:16-bookworm`, закреплённый по digest. Расширения не используются: `db/init.sql` их больше
не создаёт, а поиск по коду их не находит.

```bash
rg -ni 'pgvector|pg_trgm|trgm|similarity\(|Vector\(|embedding' backend ml tools   # ничего
```

Отсюда два следствия для DBA:

- подходит любая PostgreSQL от 14 под управлением вашего DBA, без расширений и без прав суперпользователя на
  `CREATE EXTENSION`; в `docker-compose.prod.yml` сервис `postgres` тогда просто не поднимают, а в `.env` ставят
  `POSTGRES_HOST`/`POSTGRES_PORT` вашего сервера. Схему создаёт Alembic (`alembic upgrade head` при старте backend),
  поэтому роль владельца нужна с правами на создание таблиц в своей схеме. Остальное содержимое `db/init.sql` —
  создание отдельной ограниченной роли для API — в контейнере выполняется от суперпользователя при первом старте
  тома; на базе под управлением DBA этот файл либо выполняет DBA, либо роли выдаются вашими средствами
  ([security.md](security.md) §2);
- образ намеренно взят в варианте `bookworm`: у него тот же Debian 12 и та же glibc 2.36, что у прежнего
  `pgvector/pgvector:pg16`. Это важно для существующего тома: PostgreSQL хранит версию правил сортировки
  (`pg_database.datcollversion`), и переход на образ с другой glibc (обычный тег `postgres:16` — это Debian 13 с
  glibc 2.41) дал бы постоянное предупреждение о несовпадении и потребовал бы `REINDEX DATABASE`. Проверено:
  том, созданный старым образом, стартует на новом без предупреждений, `datcollversion` совпадает с фактической
  версией, текстовые индексы и сортировка работают;
- на уже существующем томе `pgdata`, созданном прежним образом `pgvector/pgvector:pg16`, расширения остаются
  зарегистрированными — они ничему не мешают, потому что их никто не вызывает. Библиотеки `vector` в образе
  `postgres:16-bookworm` нет, поэтому перед первым `pg_dump` с такого тома лучше убрать запись, иначе дамп будет
  невосстановим на обычной PostgreSQL:

```bash
docker compose exec postgres psql -U hqai -d hqai -c '\dx'
docker compose exec postgres psql -U hqai -d hqai -c 'DROP EXTENSION IF EXISTS vector;'   # ничего от неё не зависит
```

  `pg_trgm` входит в contrib официального образа, его можно оставить. На новом томе вопрос не возникает.

## 5. Порты и переменные

| Порт | Кто | Переменная | По умолчанию |
|---|---|---|---|
| 3000 | интерфейс | `FRONTEND_PORT`, интерфейс привязки `UI_BIND` | `0.0.0.0:3000` |
| 8000 | API | `API_PORT` | `127.0.0.1:8000`, в продакшн-наложении не публикуется |
| 5432 | PostgreSQL | `POSTGRES_PORT` | `127.0.0.1:5432`, в продакшн-наложении не публикуется |

Если порт занят — поменяйте переменную в `.env`, пересоздавать ничего не нужно. Остальные переменные описаны в
`.env.example`: доступ к базе, `DEMO_API_KEY`, `DUCKDB_MEMORY_LIMIT` для конвейера, `VITE_SYNTHETIC=off` для сборки
интерфейса без синтетического слоя, `ASSISTANT_*` для ассистента (пустой ключ = ассистент выключен). Ещё одна
переменная нужна только продакшн-наложению и в `.env.example` пока не описана: `FORWARDED_ALLOW_IPS`
(раздел 3), по умолчанию `172.16.0.0/12`.

## 6. Ежедневный регламент

Смысл шагов, входной контракт выгрузок и правила публикации — в [integration.md](integration.md) §«Ночной
пересчёт». Здесь те же шаги командами, которые не требуют Python на хосте: они идут в образе `hqai-ml`, где
закреплён тот же список зависимостей (`requirements.txt`), что и у принятых запусков.

```bash
make pipe-build                                                  # один раз после обновления версии
make pipe CMD='ml/pipelines/ingest.py'                           # новые CSV -> parquet -> факты и агрегаты
make pipe CMD='ml/pipelines/flow_quantile.py --profile laptop'    # p10/p50/p90
make pipe CMD='ml/pipelines/flow_calibration.py --source-run <run-id>'
make pipe CMD='ml/pipelines/flow_hierarchy.py'
make pipe CMD='ml/pipelines/flow_pressure.py --source-run <run-id>'
make pipe CMD='ml/pipelines/signal_prioritization.py --source-run <run-id>'
make pipe CMD='tools/operational_bundle.py'                       # проекция принятых запусков в JSON
```

`make pipe CMD='… --plan'` печатает план запуска и ничего не пишет — с этого стоит начинать, чтобы увидеть
origin, окна и идентичность до того, как считать. Каждый запуск пишет `artifacts/runs/<run-id>/run.json` с хешами и
возобновляется после обрыва (`--resume <run-id>`). Контейнер монтирует рабочую копию репозитория в `/work`, потому
что в запись о запуске входит коммит, из которого он сделан; `data/` и `artifacts/` остаются на хосте.

Публикация — в образе API, он же применяет миграции:

```bash
docker compose run --rm --no-deps -v "$PWD/artifacts:/artifacts:ro" backend \
  python -m app.cli publish-operational-intelligence --bundle /artifacts/operational_intelligence/<...>.json
```

Так же публикуются `publish-review-evidence` и `publish-assurance`. Публикация транзакционная: новая версия
становится активной в конце транзакции, предыдущая остаётся в базе. После неё — `make smoke`: он печатает
идентификатор активной публикации, и это самая быстрая проверка, что интерфейс показывает новые данные.

Замерено на ноутбуке для принятых запусков (`artifacts/runs/<run-id>/run.json`): квантили 10 мин, калибровка 36 с,
иерархия 10 с, давление потока 3 мин, ранг сигналов 4 с — то есть цепочка, которая кормит экран, около 14 минут на
одну дату отсчёта. `make ingest` на 16 ГБ исходных файлов отдельно не замерялся. Шаги только для разбора человеком
в ночной цикл не входят: стресс-тест 30 мин, математические альтернативы 6,7 ч (README).

Важно: цифра «ночной пересчёт меньше двух часов» в README — расчёт для сервера 8 vCPU / 32 ГБ, а не измерение на
нём. Все приведённые здесь времена получены на ноутбуке, и первое, что стоит сделать в пилоте, — повторить эти
шаги на целевом сервере и записать реальные времена.

## 7. Резервное копирование и восстановление

```bash
make backup                                   # pg_dump custom format -> backups/hqai_<дата>.dump
make restore FILE=backups/hqai_<дата>.dump    # спросит подтверждение; --clean --if-exists --single-transaction
```

В дампе вся база: read-модели, публикации, решения специалистов, ключи (только хеши), журнал доступа. В дампе нет
`data/` (исходные и обработанные выгрузки) и `artifacts/` (запуски и бандлы) — их бэкапят файловым способом или
пересобирают конвейером; `seed/` лежит в репозитории, поэтому демо-состояние восстанавливается без дампа
(`docker compose --profile demo run --rm seed` на пустую базу).

Восстановление стоит отрепетировать до пилота: `make restore` на отдельной базе, затем `make smoke`. Дамп — это
выгрузка всей базы без шифрования, поэтому храните его там же, где остальные защищённые копии
([security.md](security.md) §4). После восстановления перезапустите backend, если он работал.

## 8. Обновление версии

1. `make backup`.
2. Получить новую версию кода и собрать образы: `docker compose -f docker-compose.yml -f docker-compose.prod.yml
   build`. Базовые образы закреплены по digest (`FROM python:3.12-slim@sha256:…`), поэтому сборка через месяц берёт
   те же биты; обновление digest — отдельное осознанное изменение (Dependabot присылает его отдельным PR).
3. `docker compose … up -d --wait` — backend сам применит миграции Alembic, затем `make smoke`.
4. Если появились новые принятые запуски — опубликовать бандлы (раздел 6).

Откат: предыдущая публикация остаётся в базе, поэтому откат данных — повторная публикация прежнего бандла. Откат
кода — сборка предыдущего коммита; необратимых миграций в проекте нет, но проверять это на дампе перед обновлением
всё равно правильно.

## 9. Закрытый контур (без интернета)

Спроектировано, но **в настоящем закрытом контуре не проверено** — репетиция входит в подготовку пилота.

В рантайме интернет не нужен: у образов нет внешних вызовов, ассистент опционален и отключается пустым
`ASSISTANT_API_KEY`. Интернет нужен только на сборку. Поэтому образы собираются на машине с доступом и переносятся
файлом:

```bash
# на машине с доступом
docker compose --profile pipelines build
docker pull postgres:16-bookworm@sha256:efedf3595f1d6f415c08568ba171029bf54052e754cc9f030e3f2412b21f3d67
docker tag  postgres:16-bookworm@sha256:efedf3595f1d6f415c08568ba171029bf54052e754cc9f030e3f2412b21f3d67 \
            postgres:16-bookworm
docker save postgres:16-bookworm hqai-backend:latest hqai-frontend:latest hqai-ml:latest | gzip > hqai-images.tar.gz
# в контуре
gunzip -c hqai-images.tar.gz | docker load
echo 'POSTGRES_IMAGE=postgres:16-bookworm' >> .env
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --wait   # без --build: образы уже загружены
```

Две детали, на которых спотыкаются: `docker pull` по digest не создаёт локальный тег, поэтому нужен `docker tag`
перед `docker save`; и `docker load` в классическом хранилище образов не восстанавливает repo digest, поэтому
закреплённая по digest ссылка в контуре не разрешится — для этого в compose предусмотрена переменная
`POSTGRES_IMAGE`, которой задают тег. Проверено на этой машине до шага `docker load`; полную загрузку в закрытом
контуре мы не воспроизводили.

Вместе с образами переносят репозиторий (в нём `seed/`, `models/`, `db/`, `docs/`, compose-файлы и `.env.example`).
Образ `hqai-ml` самый большой — 2,7 ГБ распакованным, потому что в нём весь научный набор (LightGBM, XGBoost, SHAP,
DuckDB, Polars, Arrow).

Если в контуре нужно именно собирать, а не загружать образы, понадобятся зеркала: для Python — каталог колёс
(`pip download -r requirements.txt -d wheelhouse --only-binary=:all: --platform manylinux2014_x86_64
--python-version 3.12`) и сборка с `--no-index --find-links`; для фронтенда — заполненный кеш npm и
`npm ci --offline`; для базовых образов — внутренний registry, куда они перелиты по digest. Это описание пути, а не
проверенный сценарий: ни колёса, ни `npm ci --offline` в отрезанной сети мы не прогоняли.

## 10. За чем следить

- Живость: `GET /health` (без базы) и `GET /api/v1/health` (база, свежесть витрин) — у контейнеров backend и
  frontend есть собственные healthcheck, `docker compose ps` показывает их состояние.
- Регламентная проверка: `make smoke` — три публикации и идентификатор активной, одна команда после каждого
  обновления данных и каждого обновления версии.
- Содержательные метрики и их базовые значения — [monitoring.md](monitoring.md): доля сигналов с прямой поддержкой,
  покрытие интервалов, доля сигналов, дошедших до решения человека, свежесть публикации. Пороги тревог задаются по
  первым неделям пилота, а не выдуманы заранее.
- Журналы: `docker compose logs -f backend` (в продакшн-наложении они ограничены по размеру и ротируются).
  Выгрузка stdout в журнальную систему оператора — задача контура.
- Место на диске: том `pgdata` и таблица журнала доступа растут постоянно, у журнала пока нет регламента хранения
  ([security.md](security.md) §3).

## 11. Чего в этом регламенте ещё нет

- TLS и SSO: их даёт контур перед контейнером интерфейса; в проекте нет ни того, ни другого.
- `read_only` + tmpfs для nginx и отдельный разовый сервис миграций — обсуждались, но не включены, чтобы не
  поставлять непроверенную конфигурацию.
- Полный запуск продакшн-топологии на отдельном сервере (проверено только построение конфигурации и CI).
- Смена адреса API в интерфейсе без пересборки (`API_UPSTREAM` в шаблоне nginx) и размещение интерфейса в
  подкаталоге портала.
- Регламент хранения журнала доступа и его выгрузки в SIEM.
- Замеры ночного цикла на целевом сервере: все времена выше — с ноутбука.
